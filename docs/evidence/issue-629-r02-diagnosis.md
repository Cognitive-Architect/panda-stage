## Reproduction and measurement

On Windows Server 2022 Datacenter build 20348 with AspDod/AspIdd virtual display drivers, Electron 43.1.1, use `pnpm build` then `pnpm exec electron scripts/diagnose-issue629.cjs`. The runner opens a visible production Electron window; it creates a fresh isolated root beneath `D:\PandaStage-Acceptance\issue629-*` and never opens or edits an existing user project. It uses a schema-validated synthetic project, generated 1920×1080 background PNG, full-size ordinary/Character PNGs, and a silent WAV clock. The fixture and raw per-scene events are emitted with `summary.json`. The recorded run is `D:\PandaStage-Acceptance\issue629-1wstMB\summary.json` (earlier runs `issue629-MfgxdR`, `issue629-LxveUH`, `issue629-NwoQNy`, `issue629-pvNCpe` corroborate the main cadence pattern). The test window was 1600×1000 outer / 1586×938 inner at device scale 1.5; the Stage scene canvas was 1920×1080 backing pixels and approximately 1371×771 CSS pixels.

Each scene has a 6-second Shot and the same linear 1100px Position move over 5 seconds. A: background plus one ordinary image Layer. B: background plus one Body+Face composite Character. C: background, that composite plus two single-image Characters and three ordinary images (seven visible Layers), timed Expression switch, Mouth, subtitle and an audio clip. All were ready and non-degraded before measurement. The probe records rAF callback times, requested/advanced Preview time, Stage React layout commits, DOM `data-stage-time` changes, domain/model/projection durations, composite-cache operations, synchronous Konva `drawScene`, an independent rAF, and audio `currentTime`. Counters are bounded to 20,000 events per scene. The DOM/React Stage update interval is a **committed-update upper bound / proxy**, not a direct count of pixels actually shown by the compositor; the human F07 visual observation remains separate evidence.

Idle editor and paused Preview rAF both measured 15.6 ms median (about 60Hz). An independent rAF *during* playback slowed with the Preview rAF to roughly 94–109 ms median, so this is not just a timer defect in the Preview callback. Every measured playback callback reported a visible/focused document; no max-step clamp occurred. A advanced 5437 ms of Preview time during 5449 ms wall time; B 5445/5444 ms; C 5479/5473 ms. Formal time interpolation therefore progressed with wall time but delivered far fewer intermediate visual updates. The diagnostic-only A ablation that hid **only the canvas element** with CSS `visibility:hidden` kept the same React/Stage/Konva work and produced 334 rAF callbacks and 335 Stage commits at 15.6 ms median over about 5.3 seconds; hiding the whole Stage gave the same result. This localizes the dominant simple-scene cost to the **visible full-resolution canvas presentation path** after/beyond the measured synchronous JS/model/`drawScene` segments. It does not directly time GPU raster/compositing, prove a particular GPU operation, or propose hiding/reducing the user-visible canvas as a fix.

In B, 55 composite cache rebuilds occurred for 55 Stage commits although all 55 rebuilds had **one identical Body+Face visual signature** and each had a previously cached Group. Root Position alone changed. This confirms unnecessary cache invalidation/rebuild under Position-only motion. `StagePartImages` constructs a new `orderedParts` array on each render; its layout effect depends on that array and unconditionally clears/rebuilds the cache. C had 60 rebuilds and three visual signatures because the Expression/Mouth changes genuinely alter inputs at some times; repeated rebuilds within unchanged signatures remain unnecessary. Each successful formal `buildStageRenderModel` call invokes `resolveLayerVisualParts` once per evaluated Layer; with one composite Layer per fixture scene, the recorded model-call counts imply **55 composite resolves in B and 58 in C**. The resolver's own cost was not separately timed; it is bounded by Stage model p95 0.1/0.2 ms respectively. B/C cache rebuilds consumed about 20 ms per occurrence, a real main-thread secondary contributor, but cannot explain A's similar ~10Hz behavior because A has no composite cache.

In C, 39 audio-clock samples were captured. After startup, 33 steady samples covered 3223 ms wall time, 3223 ms audio progress and 3217 ms Preview progress. Preview-minus-audio offset was about 344 ms at the first steady sample and 338 ms at the last (342 ms median): a startup offset, not accumulating drift over that interval. The synthetic WAV is silent, so this does **not** prove audible smoothness. No max-step clamping was observed. We cannot directly equate audio clock samples with visible pixels; the visual-update cadence still lagged near 100 ms.

## Decision and R03 boundary

Decision matrix: **A already bad**. Dominant measured condition is the full-size, visible Stage canvas presentation/draw pipeline during per-frame Position updates, with its expensive segment outside the measured synchronous JS calls. This is an inference from the A hide-canvas and hide-Stage ablations, not a claim of measured GPU milliseconds. Secondary: unnecessary Body+Face composite cache rebuilds on Position-only frames (~20 ms each in B/C). Lower-ranked alternatives: (1) Position interpolation / formal Shot evaluation / Stage model construction (each p95 ≤0.2 ms); (2) Preview rAF clock or max-step clamping (independent rAF slows too, zero clamps, Preview time tracks wall); (3) React reconciliation and measured synchronous Konva `drawScene` (A commit ~1 ms, `drawScene` p95 0.4 ms). Asset readiness was settled before capture; no degraded frames were observed. Thus neither changing easing nor hiding/downsizing the canvas is justified by this evidence.

**Recommended R03 repair boundary:** first isolate and reduce the per-frame *visible canvas presentation* work in the shared `StageRenderer`/Konva single 1920×1080 `<Layer>` path when only a Layer's root Position changes. A suitable first implementation experiment is to separate genuinely static content (background and unchanged Layers) from moving content so a Position-only update does not require presenting the entire combined Stage canvas each frame; compare A with the exact same canvas resolution and display scale. Do not assume that merely memoizing React/domain calculations will fix A. In the same focused Stage path, make the composite Body+Face cache invalidation depend on actual visual inputs (source/Expression/Mouth/Body/Face Placement and relevant geometry), not owner Position or a newly allocated array; verify B's Position-only rebuild count falls to zero after initial cache creation. These are R03 recommendations, **not changes made by R02**. If static/moving separation does not improve A, obtain compositor/GPU tracing before committing to a broader renderer redesign. Likely modules: `src/renderer/stage/StageRenderer.tsx`, `src/renderer/stage/CanvasStage.tsx`, and the shared render-model boundary only if tracing proves necessary.

R03's comparison should require the unchanged 1920×1080 A scene to regain near-idle rAF cadence on the same machine while its Position interpolation and visible pixels remain correct; then B should show no redundant Position-only cache rebuilds and C should be rechecked for cadence and A/V timing. If the first Stage presentation experiment does not move A, treat that as a failed hypothesis, not a reason to lower resolution or change playback time semantics.

R03 must preserve formal Position evaluation and formal Shot Preview timing; single complete Body+Face commits and shared opacity; correct invalidation for Expression, Body, Face Placement and Mouth; exact-current vs stale/fallback content; resource/readiness safety; hidden exact-capture; ordinary image Layers; and one renderer/playback/readiness truth. It must not lower canvas precision, alter schema/easing, or bypass completeness to manufacture a higher frame rate.
