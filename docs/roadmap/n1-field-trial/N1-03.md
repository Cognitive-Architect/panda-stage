# N1-03｜把摩擦变成最小修复与未来需求

> 来源：N1～N7 分阶段执行计划 v1.1。状态字段只表示本路线图任务定义，不替代实时 GitHub / MasterMind 状态；实际执行前仍需核对当时仓库、依赖和维护者授权。

## 所属阶段与边界

**阶段目标：**不再重复逐功能演示，而是从空项目完成 10～15 秒双人对白项目，交付真实摩擦账本。[R §5]

**进入条件：**采用 Day29 后已接受的可用版本；维护者授权本次采样。**离开条件：**当前承诺范围内的编辑、分镜头预览、保存重开成立，严重阻塞没有被隐藏。

**明确不做：**本阶段不要求 MP4、不要求一次连续播放所有镜头、不临时加入状态系统或动作系统；采样过程中不改代码。未来缺少的表达能力要记录，但不伪装成已承诺功能的故障。

## 本卡执行内容

**类型 / 风险：**归纳＋设计 / 低。**前置：**N1-02。

**本次成果：**有证据的修复批次，以及不抢当前主线的表达需求清单。

| 序 | 任务 | 责任区域 | 实施细节 |
|---:|---|---|---|
| 1 | 区分三种问题 | 摩擦账本 | 功能坏了、操作太累、尚无表达能力；不要统统写成 P0 |
| 2 | 合并同根因问题 | 复现与优先级 | 引用截图/步骤；判断是否版本错误、操作误解、真实缺陷或设计缺口 |
| 3 | 选择修复批次 | 当前 N1 范围 | 每批最多 3 个最影响已承诺作品的问题；其他严重问题仍保留为阻挡，不丢弃 |
| 4 | 写清 UI 修复意图 | 涉及的现有界面 | 必要时先出文字方案/概念；指出入口、主动作、提交/取消与不改项，等待确认 |
| 5 | 留下未来价值证据 | N4/N5/N6 输入 | 记录换表情、套动作、部件对齐等重复次数与无法表达的意图，不先决定实现 |

**UI/UX：**按 UX-01/11 确认修复设计；不得用新一轮全局美化替代对具体失败路径的解决。

**自动验证（V-DOC）：**每个入选问题有复现与预期；每个设计变化有确认状态；既有问题没有在排序后消失。未计算的耗时留空，不填估值。

**人工确认：**主理人检查“这是不是当时卡住的事情”；确认最小修复范围。没有主要阻塞则明确 N1-04 仅做收口复核，不硬造三项修改。

**交付与完成：**带来源的主要问题、已批准或待批准的局部方案、未来能力候选；不以这一张排序表替代产品已经修复。

**止损：**若修复开始需要整套通用动作、另一套属性区或第二播放时钟，缩回真实问题并重新说明范围。**后继：**N1-04。
